## 🛠 Schritt 5 — opena5 · VS Code‑Bridge

**Projektwurzel (Pflicht):** `/home/danijel‑jd/Dokumente/projekte/Gesammtprojekt`
**Ports:** erlaubter Pool `12344–12399` · **Port 8080 bleibt ausschließlich** für OpenWebUI (opena3) (Loopback).
**Modell:** gpt‑5‑nano · **Strict Mode:** true · **Regeln:** Append‑only · Dedupe (SHA‑256/IDs) · Keine Doppelblobs · Auditierbar.

---

### 0) Zweck & Rolle

„opena5“ verbindet deinen Quellcode‑Editor (VS Code) **mit** deinem Agent‐System‑Stack. Zweck: Änderungen, Diffs, Edit‐Aufgaben, Codeaktionen, die über den Chat, das UI oder Monitoring angestoßen wurden, gelangen ins VS Code‑Workspace und werden dort bearbeitet. Danach geht’s weiter ins Archiv („opena2“) und dann ggf. zur Ausführung („opena1“) etc.

Kurz:

* Eingang: EDIT/DIFF Aufgaben (z. B. Codeänderung angelegt via UI oder Bot)
* Verarbeitung: VS Code öffnet Workspace, zeigt die Änderung, ggf. Commit, Push
* Rückmeldung: Status/Bestätigung in Archiv + UI sichtbar gemacht

---

### 1) Topologie & Verbindungen

```
┌──────────┐    (Edit‑Aufgabe)     ┌──────────┐
│  opena3  │ ───────────────────▶ │  opena5  │
│  (UI)    │                        │  (VSCode)│
└──────────┘                        └────┬─────┘
                                         │  Änderung fertig
                                         ▼
                                   ┌──────────┐
                                   │  opena2  │ (Archivator)
                                   └──────────┘
                                         │
                                         ▼
                                   ┌──────────┐
                                   │  opena1  │ (Koordinator)
                                   └──────────┘
```

Alle Aktionen laufen über opena2 als Wahrheit („Archivator“) und opena1 als Ausführungssteuerung. VS Code (opena5) ist Teil des Rückflusses: erhält Aufgaben, macht Änderungen, spielt zurück.

---

### 2) Port‐ & Bindings‐Politik

* opena5 bindet typischerweise einen **internen API‑Port** im erlaubten Bereich z. B. `12346`.
* **Keine** Bindung auf Port 8080 erlaubt (dies bleibt ausschließlich opena3).
* Änderungen durch VS Code (z. B. über eine Extension oder CLI Hook) dürfen nicht außerhalb des Pools arbeiten.
* In `.runtime/port_leases.json` wird eingetragen:

  ```json
  {
    "leases":[
      {"agent":"opena5","port":12346,"ts":"2025-10‑22T12:00:00Z","state":"ide‑bridge"}
    ],
    "pool":"12344‑12399"
  }
  ```

---

### 3) Aufgaben, Aktionen & Persistenz

#### 3.1 Aufgaben kommen rein

Wenn z. B. über UI (opena3) oder Bot (opena4) eine Edit/DIFF Aufgabe generiert wird:

* Eventtyp: `EDIT_TASK`
* Dedup‑Key: `file_path + sha256(diff_contents)`
* Persistenz: `archivp/.../patches/src/{file_path}/{sha256(diff)}.json` (append only)
* Audit‑Eintrag: `archivp/index.jsonl` mit Zeitstempel, Actor=open­a3/opena4, Event=EDIT_TASK

#### 3.2 VS Code Bridge nimmt entgegen

* VS Code (opena5) holt sich die Aufgabe (z. B. via local API Port 12346 `/tasks/poll`)
* Öffnet das angegebene `file_path` im Workspace, zeigt Diff/Anweisung
* Entwickler übernimmt: ändert Code, speichert, ggf. commit & push (oder automatisiert)
* Nach Abschluss schreibt opena5:

  * Safepoint CMD: `SP<ts>_opena5→opena2_CMD.json` mit Payload `{ file_path, diff_sha256, author }`
  * Persistenz der Änderung: ggf. `blobs/patches/src/...`
* opena2 schreibt RESP: `SP<ts>_opena2→opena5_RESP.json` mit Ergebnis (`status: ok/failed`, details)
* Audit‑Index ebenfalls ergänzt

### 4) VS Code Extension / CLI Integration

  * Anzeige neuer Aufgaben (z. B. via VS Code Notifications oder View)
  * Öffnen des `file_path` zur Bearbeitung
  * Nach „Abschließen“ Button oder Kommando: sendet Abschluss‑Payload an opena5 API
* Alternativ: CLI Hook, die beim Commit/Push automatisch die Änderung meldet

Technisch sind für die Extension die offiziellen VS Code APIs relevant. ([code.visualstudio.com][1])

### 9) Fehlerbilder & Recovery

* Doppel‑Diffs (Same sha256) → kein neuer Blob, nur Referenz; keine Aktion durch VS Code

* Port Konﬂikt: opena5 bindet nicht erlaubten Port → Safepoint CMD erzeugt, Lease gewechselt
* VS Code nicht erreichbar: opena5‐Bridge erkennt Ausfall, schreibt ALERT → opena20 erkennt Latenz/Fail

* Port Governance eingehalten (12344–12399), 8080 tabu.

# 🧭 Schritt 4 — opena4 · Telegram‑Bridge (Webhook‑Betrieb)

**Projektwurzel (Pflicht, für alle Schritte):** `/home/danijel‑jd/Dokumente/projekte/Gesammtprojekt`

**Modell:** `gpt‑5‑nano` · **Strict Mode:** `true` · **Regeln:** Append‑only · Dedupe (SHA‑256/IDs) · Keine Doppelblobs · Auditierbar

## 0) Zielbild

* opena4 übernimmt die Verbindung zu Telegram im **Webhook‑Modus** (Push).
* Alle Updates von Telegram landen **zuerst** bei opena2 (Archivator) bzw. über eine Folge von Hops: opena4 → opena2 → opena1 → … etc.
* UI (opena3) und VS Code‑Bridge (opena5) greifen nur auf verifizierte Daten zu.
* Knopf/Link‑Aktionen in OpenWebUI triggern agentenbezogene Aktionen via opena4 → opena2 → opena1 etc.
* Der Portpool‑ und Governance‑Rahmen wird strikt eingehalten: 8080 ist **nur** für opena3, Webhook‑Service läuft z. B. auf 12347.

## 1) Topologie (Webhook‑Push)

```
Internet (Telegram) ──HTTPS──▶ NGINX (TLS) ──proxy_pass──▶ 127.0.0.1:12347 (opena4_webhook)
                                                  │
                                                  ▼
                                       archivp/... (opena2)
                                                  │
                                                  ▼
                                       Koordination (opena1)
                                                  │
                                                  ▼
                                       UI (opena3, 8080 Loopback)
```

**Hinweis:** 8080 bleibt **ausschließlich** opena3 vorbehalten. Der Webhook‑Endpunkt läuft **nicht** auf 8080, sondern typischerweise auf einem Port im Pool (z. B. 12347).

## 2) BotFather & Telegram‑Basics

### 2.1 Bot erstellen

* In Telegram: Suche `@BotFather`.
* Sende `/newbot` → gib **Name** + **Benutzername** (endet üblicherweise auf *bot*) ein.
* Kopiere den API‑Token (z. B. `123456:ABCDEF…`) → trage ihn in `.env` ein:

  ```env
  TELEGRAM_BOT_TOKEN=123456:ABCDEF...
  TELEGRAM_WEBHOOK_SECRET=<mindestens 16 zeichen>
  TELEGRAM_ALLOWED_USERS=123456789,987654321
  ```
* Optional: `/setdescription`, `/setabouttext`, `/setcommands` (z. B. `start`, `health`, `start_agent`, `stop_agent`), `/setprivacy` (z. B. private Nachrichten)

### 2.2 Webhook vs. Long‑Polling

* **Long‑Polling**: Einfacher Setup, Bot fragt Telegram regelmäßig ab (`getUpdates`).
* **Webhook (empfohlen für Produktion):** Telegram sendet Updates an deinen HTTPS‑Endpoint. Vorteil: Echtzeit, effizienter. ([Telegram][1])
* Voraussetzungen laut Telegram: HTTPS mit TLS1.2+, öffentlicher Port (443, 80, 88 oder 8443) oder via Reverse Proxy. ([Telegram][1])

### 2.3 Webhook setzen

Zum Beispiel mit `curl`:

```bash
curl -X POST "https://api.telegram.org/bot<TELEGRAM_BOT_TOKEN>/setWebhook" \
     -d "url=https://dein.host/telegram/webhook&secret_token=<WEBHOOK_SECRET>"
```

Antwort sollte etwa sein: `{"ok":true,"result":true,"description":"Webhook was set"}` ([Stack Overflow][2])

## 3) Persistenz, Dedupe & Pfad‑Layout

* Jede eingehende Telegram‑Update‑Payload wird **kanonisiert** und mit SHA‑256 gehasht.
* Gegenprüfung in `docs/DEDUP_INDEX.json`. Existiert Hash bereits → **keinen neuen Blob**, nur Referenz/Audit.
* Ablage‑Beispiele im Projektverzeichnis:

  ```
  /home/danijel‑jd/Dokumente/projekte/Gesammtprojekt/
    ├─ archivp/

    │    │    └‑ blobs/
    │    │         ├‑ tg/in/{chat_id}/{message_id}.json
    │    │         ├‑ tg/out/{chat_id}/{sha256}.json
    │    │         ├‑ tg/cmd/{chat_id}/{message_id}.json
    │    │         ├‑ tg/file/sha256/<ab>/<hash>
    │    │         └‑ alert/{sha256}.json
    │    └─ index.jsonl   # Audit‑Index (append‐only)
    ├─ docs/
    │    ├─ DEDUP_INDEX.json
    │    ├─ HEADS.json
    │    ├─ HEALTH_RECORDS.jsonl

    ├─ .runtime/
    │    └─ port_leases.json
    ├─ logs/
    │    └─ opena4.log
  ```
* Dedupe‑Key Beispiele:

  * `chat_id + message_id` für eingehende Nachricht (`MSG_IN`)

## 4) NGINX (TLS‑Terminator & Proxy)

Zum Beispiel: `docs/examples/nginx_opena4_webhook.conf`

* TLS auf Port 443 terminieren (z. B. mit Let’s Encrypt)
* Methode: `POST` akzeptieren
* Proxy zu `127.0.0.1:12347` (Webhook Service von opena4)

## 12) Fehlerbilder & Recovery

* **429/Rate‑Limit** von Telegram: Backoff → ALERT in opena2 → erneuter Versuch idempotent über `message_id`.
* **Bad Token**: sofortige NACK → Dienst anhalten → Tokenrotation erforderlich.
* **Port‑Konflikt**: opena4 bindet nicht erlaubten Port → Lease‑Wechsel → Safepoint CMD/RESP auditiert.
* **Dedupe‑Treffer**: Bereits vorhandener Hash → kein neuer Blob, nur Referenz im Audit‑Index.
* **Unreachable Webhook**: HTTPS nicht erreichbar (Firewall/Cert) → Telegram setzt webhook zurück → Fehler in health/Metrics.
* **Conflict bei Write**: atomare Write‑Guard schlägt fehl → Dienst zurück in Safe‑State, Audit schreibt FAIL.

## 3) Persistenz, Dedupe & Pfad‑Layout (korrigiert)

### 3.1 Regeln

* **Append‑only**: Es wird niemals etwas überschrieben oder gelöscht.
* **Dedupe**: Vor jedem Speichern wird die Nachricht (Telegram Update, File, Alert) **kanonisiert**, dann mit **SHA‑256** gehasht.
* Wenn der Hash bereits existiert → **kein neuer Blob**, nur ein Eintrag im Audit‑Index (`index.jsonl`).
* Jeder Speichervorgang erzeugt einen **Safepoint** (CMD oder RESP) unter `archivp/YYYY/MM/DD/`.
* Die Indexdateien (`DEDUP_INDEX.json`, `HEADS.json`, `INTEGRITY_TREE.json`) bilden die Referenz der Datenintegrität.

---

### 3.2 Dedupe‑Keys (nach Typ)

| Event‑Typ  | Dedupe‑Key                       | Pfad                                       |
| ---------- | -------------------------------- | ------------------------------------------ |
| BOT_CMD    | `chat_id + message_id`           | `blobs/tg/cmd/{chat_id}/{message_id}.json` |
| MSG_IN     | `chat_id + message_id`           | `blobs/tg/in/{chat_id}/{message_id}.json`  |
| MSG_OUT    | `chat_id + sha256(payload)`      | `blobs/tg/out/{chat_id}/{sha256}.json`     |
| ATTACHMENT | `sha256(file)`                   | `blobs/tg/file/sha256/<ab>/<hash>.json`    |
| ALERT      | `sha256(alert_type + ts_bucket)` | `blobs/tg/alert/{sha256}.json`             |

---

```plaintext

    └── 2025/

            └── 22/
                ├── SP1697974712_opena4→opena2_CMD.json       # Safepoint: CMD an Archiv
                ├── SP1697974713_opena2→opena4_RESP.json      # Safepoint: Archiv-Antwort
                └── blobs/
                    └── tg/
```

### 3.7 Write‑Verhalten

* **Vor jedem Write:**

  * SHA‑256 berechnen
  * DEDUP_INDEX prüfen
  * Wenn **nicht vorhanden:** Datei schreiben + Index aktualisieren
  * Wenn **schon vorhanden:** nur `index.jsonl` erweitern
* **Pfadvalidierung:** Nur whitelisted extensions + bekannte Unterverzeichnisse (`in`, `out`, `cmd`, `alert`, `file`).
* **atomare Writes:** Via temp file + move, um Race Conditions zu vermeiden
