Kernregeln · Option-2-Flow

Heilige Regel

Der einzige zulässige Routing-Flow für fachliche Anfragen:

OpenAI → opena1:12344 → opena2:12345 → kordp:12346 → Tools/Agents → opena2 → opena1 → OpenAI

  • Keine Direktverbindungen von OpenAI zu Tools/Agents.
  • Keine Direktverbindung von opena1 zu kordp ohne CMD-Safepoint bei opena2.
  • Jeder CMD und jeder RESP wird als Safepoint mit Unicode-Pfeil → archiviert.
  • Archivpfad: archivp/YYYY/MM/DD/SP<TS>_src→dst_kind.json
CMD Safepoints RESP Safepoints Dispatch über kordp Append-only Archiv

Port- & Sicherheits-Policy

8080 Backend-Verbot

opena1 respektiert strikt die PORTIER 3.0 Hafenrichtlinie:

  • Backend-Services: 12344–12399
  • opena1: 12344, opena2: 12345, kordp: 12346, Dashboard: 12349
  • Port 8080 ist ausschließlich für externe UI (z.B. OpenWebUI) reserviert – kein Backend.
  • Externe Services (außerhalb PORTIER-Core):
    • OpenWebUI: 3000 (Upstream, via Adapter 12347/12350)
    • ComfyUI: 8188 (Upstream, via Adapter 1235x)
  • Anfragen, die Backend auf 8080 konfigurieren wollen, werden abgelehnt und als Sicherheitsereignis geloggt.

Sensitive Felder (z.B. password, api_key, token, secret) werden in Safepoints redigiert.

Routing-Matrix · Zuständigkeiten

Koordinator-Sicht

opena1 delegiert Anfragen ausschließlich über kordp an spezialisierte Agenten. Typische Targets (Beispiele):

  • telep → opena4_telegram (Messaging / Telegram Bot) · Port 12348
  • browserp → opena6_browser (Browser Automation) · Port 12350
  • mailp → opena7_email (E-Mail Agent) · Port 12351
  • htmlp → opena15_html (HTML-Generierung für Landingpages) · Port 12359
  • shopp → opena16_shop (Shop-Generator) · Port 12360
  • workflowp → opena21_workflow (Workflow Engine) · Port 12365

opena21 kann diese Matrix erweitern und live aus der Registry laden, z.B. über agent_registry_opena1.py oder ein zentrales Routing-Register.
